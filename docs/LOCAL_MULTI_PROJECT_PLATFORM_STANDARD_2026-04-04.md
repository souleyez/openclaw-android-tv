# 本地多项目平台与应用边界规范

## 1. 总体结构

当前按你确认后的口径，仓库边界应固定为：

- `home`
  - 平台层仓库
  - 承接公共后端与公共管理后台
- `ai-data-platform`
  - 应用之一：AI 智能助手
- `Sonance`
  - 应用之一：声临
  - iOS / Android / Web 三端一套代码
- `openclaw-android-tv`
  - 应用之一：百万龙虾
  - 只适配 Android TV

以后新增应用，也都按这个结构接入：

- 一个公共平台仓库
- 多个独立应用仓库
- 所有应用共用平台后台

## 2. 平台层职责

平台层仓库只有一个：`home`。

`home` 负责所有跨应用复用能力：

- 公共管理员登录与会话
- 应用目录
- 应用访问控制
- 共用模型池
- provider key 管理
- 通用治理配置
- 通用 release / config 发布
- 平台级广播编排与投递
- 审计日志
- 公共管理后台

平台层不负责：

- 某个应用自己的业务内容
- 某个应用自己的客户端体验
- 某个应用自己的账单、节目、聊天、页面、站点或播放逻辑

一句话说清楚：

- 只要以后可能被多个应用复用，就归 `home`
- 只要明显只属于某个应用，就留在对应应用仓库

## 3. 应用层职责

### `ai-data-platform`

这是 AI 智能助手应用仓库，不再定义为平台仓库。

它应该保留：

- AI 智能助手应用自己的前后端逻辑
- 应用自身数据模型
- 应用自身运行时
- 对平台模型池、治理、发布、广播的消费逻辑

它不应该继续新增：

- 平台级管理员体系
- 平台级模型池源头
- 平台级通用后台
- 平台级应用目录
- 平台级广播中心

如果这个仓库里当前还暂存着平台控制面代码，那是迁移中的临时状态，不是目标边界。

### `Sonance`

这是声临应用仓库。

它应该保留：

- 声临三端共享业务代码
- 声临自己的运行时逻辑
- 声临自己的内容域和业务域
- 接平台广播后的本地执行逻辑

它不应该继续保留或扩展：

- 第二套平台管理后台
- 第二套平台模型池
- 第二套通用 OTA 平台
- 第二套平台管理员登录

### `openclaw-android-tv`

这是百万龙虾应用仓库。

它应该保留：

- Android TV 端专属 UI 和系统适配
- Android TV 端运行时和设备侧逻辑
- 接平台广播、release、config 的消费逻辑

它不应该保留：

- 平台管理员能力
- provider key
- 平台模型池调度源头
- 平台级发布中心

## 4. 仓库名、产品名、应用标识分开管理

后续必须区分三件事：

- 仓库名
- 产品名
- 平台里的稳定 `projectKey`

不要把这三者强行绑死。

建议关系：

- 仓库 `home`
  - 产品：公共平台
  - 不是普通应用，不参与应用 projectKey 命名
- 仓库 `ai-data-platform`
  - 产品：AI 智能助手
  - `projectKey` 建议保持稳定，不跟仓库名强耦合
- 仓库 `Sonance`
  - 产品：声临
  - `projectKey` 可直接用 `sonance`
- 仓库 `openclaw-android-tv`
  - 产品：百万龙虾
  - `projectKey` 建议用稳定应用标识，不一定要等于仓库名

规范重点是：

- 仓库可以改名
- 产品名可以调整
- `projectKey` 一旦进入平台数据模型，就应保持长期稳定

## 5. 共享能力的收口规则

只要下面这些能力被两个及以上应用共用，就必须进入 `home`：

- 管理员认证
- 模型池
- provider key 管理
- 通用 release 发布
- 通用配置下发
- 通用治理
- 平台广播
- 审计日志
- 应用目录

应用仓库最多只能做三类事情：

- 消费平台接口
- 缓存平台数据
- 执行本地应用逻辑

禁止继续在多个应用仓库里并行扩同一套平台能力。

## 6. 所有应用必须保留的固定平台接入面

每个应用都可以独立运行，但必须固定能接受 `home` 的平台广播。

最小入站接口固定为：

- `GET /internal/platform/health`
- `POST /internal/platform/broadcasts`

建议语义：

### `GET /internal/platform/health`

用于平台判断应用是否在线、是否可接收广播。

返回建议：

```json
{
  "status": "ok",
  "projectKey": "sonance",
  "acceptsBroadcast": true,
  "version": "2026.04.04"
}
```

### `POST /internal/platform/broadcasts`

用于平台向应用投递统一广播。

请求建议：

```json
{
  "broadcastId": "bc_20260404_001",
  "projectKey": "sonance",
  "kind": "notice",
  "scope": "global",
  "title": "platform message",
  "body": "text body",
  "payload": {},
  "createdAt": "2026-04-04T12:00:00.000Z",
  "expiresAt": null,
  "idempotencyKey": "bc_20260404_001"
}
```

响应建议：

```json
{
  "status": "accepted",
  "broadcastId": "bc_20260404_001",
  "projectKey": "sonance",
  "receivedAt": "2026-04-04T12:00:01.000Z",
  "mode": "async"
}
```

广播处理要求：

- 必须支持幂等
- 必须允许异步入队
- 平台离线时应用仍可独立运行
- 应用离线时平台可重试广播

## 7. 现阶段清理原则

### 对 `home`

后续所有公共平台开发优先放这里。

包括：

- 公共 control plane
- 公共后台
- 平台目录
- 平台广播
- 平台治理

### 对 `ai-data-platform`

后续清理方向是：

- 保留 AI 智能助手应用逻辑
- 停止继续把它当公共平台主仓开发
- 把通用平台能力逐步迁到 `home`

### 对 `Sonance`

后续清理方向是：

- 保留声临应用逻辑
- 保留三端共享业务代码
- 删掉或冻结重复的平台能力
- 改成消费 `home`

### 对 `openclaw-android-tv`

后续清理方向是：

- 保留 Android TV 应用本体
- 保留设备端逻辑
- 通过固定平台接口接 `home`
- 不再重复造平台控制面

## 8. 本地开发默认规则

从现在开始，本地开发按下面顺序做判断：

1. 先判断这是平台能力还是应用能力。
2. 平台能力直接进 `home`。
3. 应用能力只进对应应用仓库。
4. 应用如需接收统一控制，走固定广播接口。
5. 新增应用时，先在 `home` 注册应用目录，再接广播接口。

## 9. 提交前检查项

如果一项改动可能影响边界，提交前至少检查：

- 有没有把平台能力继续写进应用仓库
- 有没有在两个应用里重复扩同一套公共功能
- 有没有让应用依赖平台在线才能启动
- 有没有保留固定的广播接入面
- 有没有同步更新文档

## 10. 当前结论

按你现在确认的架构，正确的理解是：

- `home` 是平台
- `ai-data-platform` 是应用
- `Sonance` 是应用
- `openclaw-android-tv` 是应用

不是：

- `ai-data-platform` 继续充当平台主仓
- 每个应用各保留一套自己的共享后台

后续所有“公共后端管理平台”开发，都应以 `home` 为归属仓库。
