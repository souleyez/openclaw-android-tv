## 2. 文档目标

定义 OpenClaw Android / Android TV Assistant 的订阅结构、充值方案、设备共享规则、财务看板指标和基础风控原则，为商业化 MVP 提供统一运营框架。

## 3. 商业模式

产品采用“订阅制 + Token 充值制”双轨模式。

- 订阅制负责覆盖基础语音控制、设备共享和日常使用额度
- Token 充值负责覆盖高频调用、高成本模型和超额使用

## 4. 套餐建议

## 4.1 基础版

- 适用对象：个人单设备用户
- 建议设备数：1
- 包含：
  - 基础语音控制
  - 大字字幕
  - 基础角色
  - 基础 Token 配额

## 4.2 家庭版

- 适用对象：家庭多设备用户
- 建议设备数：3
- 包含：
  - 多设备共享
  - 更高 Token 配额
  - 优先使用更稳定模型路由

## 4.3 高级版

- 适用对象：重度用户或小型场景部署
- 建议设备数：5+
- 包含：
  - 更高并发额度
  - 更高 Token 配额
  - 高级角色资源
  - 更高优先级模型

## 5. 充值方案

建议配置三档 Token 包：

- 小额包：用于轻度补充
- 中额包：用于家庭版高频问答
- 大额包：用于高级版或运营推广

原则：

- 充值 Token 独立于订阅内配额
- 先消耗订阅内额度，再消耗充值额度
- Token 过期规则需明确，建议首期不设置过短有效期

## 6. 支付方式优先级

### MVP 必做

- 信用卡支付
- 国际银行卡支付

### 二期预留

- 稳定币支付
- 区域性本地支付

原因：

- MVP 要先保证支付闭环与合规性
- 稳定币适合后续高客单价或跨区用户，但不应阻塞首发

## 7. 设备共享规则

### 基础规则

- 每个套餐有明确设备上限
- 同一账号可查看所有已绑定设备
- 设备达到上限后，新增设备必须解绑旧设备或升级套餐

### 并发规则

- 同时活跃设备数不得无限制
- 高频控制或问答请求应按账号与设备双重限流

### 建议初始值

- 基础版：1 台设备，1 活跃会话
- 家庭版：3 台设备，2 活跃会话
- 高级版：5 台设备，3 活跃会话

## 8. Token 扣费策略

### 不建议重点计费的行为

- 简单打开 App
- 简单播放控制
- 基础字幕反馈

### 建议计费的行为

- 复杂问答
- 多轮上下文聊天
- 高成本模型调用
- 高级角色能力

### 成本优化原则

- 能用规则引擎解决的动作尽量不调用大模型
- 简单意图优先走低价模型
- 仅在需要时调用高质量模型

## 9. 收入与成本指标

### 收入指标

- 日收入
- 月收入
- 月续费金额
- 充值金额
- ARPU

### 成本指标

- 日模型调用成本
- 每用户平均模型成本
- 各供应商成本占比
- 支付通道手续费

### 核心经营指标

- 毛利率
- LTV
- 设备平均绑定数
- 订阅续费率

## 10. 财务面板建议

后台建议至少支持以下面板：

### 收入总览

- 订阅收入
- 充值收入
- 退款金额
- 净收入

### 模型成本总览

- 按供应商统计成本
- 按模型统计成本
- 按国家或区域统计成本

### 用户价值分析

- 付费用户数
- 家庭版占比
- 高级版占比
- 设备共享分布

### 风控面板

- 高频绑定/解绑用户
- 高频调用高成本模型用户
- 可疑地区切换账户

## 11. 风控策略

### 支付风控

- 支付失败重试次数限制
- 异常退款记录
- 可疑高频小额支付预警

### 设备风控

- 同账号频繁切换设备触发预警
- 同时在线设备异常升高触发限流
- 异常地区登录触发人工审核或短信验证

### 模型成本风控

- 单日高成本模型预算上限
- 异常调用峰值告警
- 按套餐限制高阶模型可用次数

## 12. 运营策略建议

### 首发阶段

- 以家庭版为主打套餐
- 强调“多设备共享 + 多语言语音控制”
- 重点强调客厅、老人、小孩使用场景

### 增长阶段

- 结合充值包做活动促销
- 对高价值用户引导升级高级版
- 引入长期订阅折扣

### 稳定阶段

- 观察不同模型供应商成本占比
- 动态优化套餐配额
- 优化高毛利用户分层

## 13. 退款与补偿原则

建议建立明确规则：

- OTA 或服务异常导致大面积不可用时，可发放补偿 Token
- 支付成功但账户未到账，优先人工补单
- 高频滥用与风险账户不自动退款

## 14. 运营后台最小功能

MVP 管理后台至少需要：

- 套餐配置
- Token 包配置
- 订单列表
- 钱包余额调整
- 收入总览
- 模型成本总览
- 风控事件列表

## 15. 执行建议

### 第一阶段

- 固定 2 到 3 个套餐
- 固定 3 档 Token 包
- 只接入信用卡支付

### 第二阶段

- 观察付费转化和成本
- 优化设备共享规则
- 增加活动价格与运营券

### 第三阶段

- 稳定币支付
- 区域化价格策略
- 更复杂的结算与税务支持

## 16. 结论

MVP 阶段不应把商业模型设计得过于复杂。最重要的是先打通：

- 订阅支付
- 设备共享
- Token 充值
- 模型成本可观测

只要这四个闭环成立，后续无论是扩套餐、扩支付方式还是扩模型供应商，都会容易很多。
